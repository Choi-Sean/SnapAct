# apps/ios/ — setup notes

Everything in `ShareExtension/` was written blind: this environment has no
macOS/Xcode, so none of it has been compiled, run, or debugged. Treat it as
a strong first draft of the pipeline logic (ported 1:1 from
`apps/expo/src/layer0/`, which *is* tested), not verified native code. The
first real build needs to happen on a Mac (or a rented one — see the
earlier conversation about AWS EC2 Mac / MacStadium / MacinCloud) with
someone iterating in Xcode until it compiles and runs cleanly, especially
around the extension's memory ceiling — that's exactly the risk this whole
split was meant to manage, and it can only be checked on a real device with
Instruments attached.

## 1. Resolve the expo-share-intent conflict first

`apps/expo` already has `expo-share-intent` installed, and its config
plugin auto-generates its **own** iOS Share Extension target during
`expo prebuild` (bundle id `com.snapact.app.share-extension` — you can see
it by name in the EAS build logs from this session). That extension is a
thin JS-forwarding one: it just captures the shared image and hands it to
the RN app via the `snapsist://` URL scheme.

Adding this hand-written `ShareExtension` target on top, without touching
that, means **two share extensions** would show up for the same "Share a
photo" action, both claiming to be Snapsist. Before wiring this into
Xcode, pick one:

- **Replace it (matches the plan discussed this session):** drop
  `expo-share-intent`'s iOS piece. If the package doesn't offer an
  iOS-off/Android-only option, remove the plugin's `iosActivationRules`
  config (or the whole package, if it turns out to only exist for iOS) and
  let this native target be the only iOS share extension. Keep
  `expo-share-intent` for Android — `apps/expo/App.tsx`'s `useShareIntent()`
  wiring is unaffected on that platform.
- **Keep both, scope them differently:** unlikely to be worth the
  confusion of two "Snapsist" entries in one share sheet — not recommended.

## 2. Add the Xcode target

This repo has no checked-in `ios/` Xcode project (`apps/expo` is Expo
managed workflow — the project is generated by `expo prebuild` /
EAS Build). To get an Xcode project to add a target to:

```bash
cd apps/expo
npx expo prebuild --platform ios
```

Then in Xcode (`apps/expo/ios/mobile.xcworkspace`... or whatever the
generated workspace is named):

1. File → New → Target → Share Extension, name it `ShareExtension`,
   bundle id `com.snapact.app.share-extension` (reusing the id
   expo-share-intent had, if you removed it per step 1 — keeps App Store
   Connect from needing a new identifier registered).
2. Delete the boilerplate files Xcode generates for the new target
   (`ShareViewController.swift`, `MainInterface.storyboard`, `Info.plist`)
   and add the files from this folder instead: `ImageClassifier.swift`,
   `TextRecognizer.swift`, `MedicationExtractor.swift`,
   `MedicationReminderSaver.swift`, `LayerZeroAnalyzer.swift`, `L10n.swift`,
   `ShareResultView.swift`, `ShareViewController.swift`, `Info.plist`.
3. Set the target's deployment target to iOS 16.4 (matches
   `apps/expo`'s deployment target — `VNRecognizeTextRequestRevision3`
   needs iOS 16+ for ko/ja/zh anyway, see `apps/expo/src/layer0/textRecognition.ts`'s
   comment and `backend/app/pricing.py`'s architecture doc for why).
4. Add the `NSExtensionActivationSupportsImageWithMaxCount` rule from this
   folder's `Info.plist` in target settings if Xcode's generated one
   doesn't already match it (single image only, for now — batch share
   would need a bigger UI change, out of scope here).
5. Capabilities → add **Reminders** (`EventKit.framework` should
   autolink; if not, add it manually under "Frameworks and Libraries").
6. Re-run `eas build --profile development --platform ios` once this
   compiles locally — EAS's cloud Mac builders will pick up the new
   target the same way they picked up expo-share-intent's.

## 3. Known gaps in this first pass

- **No Layer 1 fallback network call.** `business_card` / `receipt` /
  `event_flyer` currently just show "open the app" (`ShareResultView`'s
  `.needsLayer1` case) instead of calling `backend/app/main.py`'s
  `/analyze` directly from the extension. Doing that properly needs the
  extension to read the signed-in session token — `apps/expo/src/auth.ts`
  stores it via `expo-secure-store` (iOS Keychain), which the extension
  can only read if both targets share a Keychain Access Group entitlement.
  That's a real interop risk worth its own focused pass rather than
  guessing the exact Keychain query attributes blind.
- **Medication reminder time picker is skipped.** The RN app
  (`apps/expo/src/AnalyzeScreen.tsx`'s `TimeConfirmModal`) prompts for a
  time when the photo doesn't have one written on it; the extension just
  defaults to 09:00 to keep the "few seconds, no extra taps" flow. Worth
  revisiting once the base pipeline is proven.
- **No App Group / shared history.** A reminder saved from the extension
  won't show up in the RN app's History tab (that's sourced from
  on-device storage the extension never writes to). Would need a shared
  App Group container both targets write to.
